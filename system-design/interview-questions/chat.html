Chat

Requirements · Core entities · API or system interface · High-level design · Deep dives

1. Requirements

Functional requirements

Create member-scoped conversations; send text messages; receive live messages and retrieve missed history. Limit groups to 100 members.

Nonfunctional requirements

  1. NFR1: assume one million connections and 20,000 peak messages/second, targeting same-region online delivery p95 below 200 ms.
  2. NFR2: preserve one committed order per conversation and one stored message per sender/clientMessageId; delivery may repeat.
  3. NFR3: lose no acknowledged message through one zone failure.
  4. NFR4: permit only current members to send/read and stop removed members receiving new server-delivered content within five seconds.

Out of scope

Calls, media attachments, end-to-end encryption, read receipts, and giant broadcast channels are excluded. Previously downloaded messages cannot be recalled.

2. Core entities

Conversation(conversationId, nextSequence), Membership(conversationId, userId, role), and Message(conversationId, sequence) are authoritative. Messages include senderId, clientMessageId, and text. A unique sender/clientMessageId key within the conversation prevents duplicate storage. Session(userId, deviceId) tracks ephemeral socket routing, not message durability.

3. API or system interface

POST /conversations {members} uses Idempotency-Key and returns 201 with conversationId. POST /conversations/{id}/messages {clientMessageId, text} returns committed sequence; identical retries return that sequence and changed text returns 409. Invalid size returns 422. GET /conversations/{id}/messages?afterSequence&limit returns up to 100 ordered messages and a next cursor. WebSocket subscribe accepts conversationId and lastSeenSequence after authentication. All operations check membership; inaccessible conversations return 404. DELETE /conversations/{id}/members/{userId} requires group-admin authority and is idempotent. Unavailable ordering authority returns 503, not a success receipt.

4. High-level design

    Client --> ChatServer
    ChatServer --> ConversationDatabase

  1. Create the conversation and memberships transactionally.
  2. Check membership, allocate a sequence, insert the message, and acknowledge commit.
  3. Push committed messages to sockets; reconnecting clients fetch history after their last contiguous sequence.

5. Deep dives

Trade-offs and bottlenecks

One server makes routing easy but cannot hold every socket or survive failure. Separate connection gateways from conversation owners. Global ordering would serialize unrelated chats; per-conversation ordering is sufficient. Push accelerates delivery, while the durable log remains the recovery mechanism when gateways lose messages.

Scale estimate: connections and message retention

At an assumed 20 KB of connection state, one million sockets need 20 GB across gateways before buffers and runtime overhead. With 10,000 connections/gateway, start capacity testing near 100 gateways plus failover headroom. Assume 5,000 average messages/second at 1 KB: 432 GB/day raw, or 1.296 TB/day for three copies before indexes. Set history retention explicitly instead of keeping all data in memory.

Routing and bounded delivery

Route conversation commands by conversationId hash; route sockets by userId and deviceId through a shared presence directory. Fan-out workers consume committed message events and forward to currently connected devices. A stale directory entry causes a missed push, not lost history. Clients buffer out-of-order sequences briefly and request gaps; they deduplicate by conversation and sequence. Limit socket output queues and disconnect slow consumers with a reconnect cursor rather than growing memory indefinitely. Heartbeats spread across time avoid synchronized traffic spikes. Partition work across conversations; the 100-member cap limits any single message's fan-out.

Commit, retry, and membership boundaries

A quorum-replicated conversation partition serializes membership changes and message appends. Allocate sequence, persist deduplication information, and record an outbox event in one transaction before acknowledgement. Leader fencing prevents two owners assigning conflicting sequences. History and send authorization use current membership. Gateways obtain membership leases lasting at most five seconds from the start of an authoritative check; delivery stops when leases expire unless renewed. Removal events close sockets promptly, while expiry handles missed invalidations. During quorum or authorization outages, reject writes and stop expired subscriptions. Retain deduplication identities for the supported message-history lifetime, with matching retry limits documented.

Check the design

NFR1 is addressed by routing and bounded delivery; NFR2 also needs commit and retry boundaries; NFR3–4 depend on durable commit and membership enforcement. Kill the owner after commit but before acknowledgement: retry returns the same sequence, reconnect yields no gaps, and removed members receive nothing beyond the five-second lease window.
