Design a rate limiter

1. Requirements

Functional: evaluate a request against a tenant policy; update that policy; inspect remaining allowance. Assume token-bucket semantics: a burst capacity and a continuous refill rate.

Non-functional assumptions: N1: decision latency p99 below 10 ms within one region. N2: sustain 100,000 decisions/s peak across one million active keys. N3: zero token overspend from concurrent requests or acknowledged-state loss during a single-node failure.

2. Out of scope

Exclude global multi-region quotas, billing, bot detection, and rules combining several independently sharded buckets. A request consumes exactly one bucket.

3. Core entities

Policy is keyed by (tenant, policy ID), with version, capacity, and refill rate. Bucket uses (tenant, policy ID, subject), storing balance and refill timestamp. Decision uses (bucket, request ID), with a bounded retry lifetime and authenticated gateway issue time. Under a fixed policy, accepted costs never exceed initial capacity plus elapsed refill; balances never become negative.

4. API

POST /decisions accepts policy ID, subject, cost, and request ID; returns allowed, remaining, policy version, and retryAfterMs. Gateway service credentials restrict tenant and subject namespaces. A denied decision is a normal response; malformed costs return 400, unauthorized policies 403, unavailable owners 503. Reuse the request ID within the advertised 60-second retry window. Expired IDs return 409 rather than silently granting a fresh retry. PUT /policies/{id} requires tenant-admin permission and expected version; conflicts return 409. GET /policies/{id}/buckets/{subject} returns an authorized, non-reserving snapshot.

5. Basic design

    Gateway --> Limiter
    Admin --> Limiter
    Limiter --> Database
  1. Store policy updates transactionally, incrementing their version.
  2. For each decision, lock the bucket, refill to capacity, subtract cost if sufficient, and save the response with its request ID.
  3. Read bucket state and calculate its current allowance without consuming tokens.

6. Trade-offs and bottlenecks

A database transaction makes concurrent deductions understandable but adds a write round trip to every request. Per-gateway local buckets remove that hop but multiply the permitted burst unless allowance is explicitly leased. Choose authoritative buckets rather than accepting that overshoot.

7. Scale estimate

Assume 20,000 decisions/s average and fivefold peak. At 200 bytes per bucket, one million buckets occupy 200 MB raw. A 60-second deduplication window at peak holds six million responses; at 100 bytes each that is another 600 MB before indexes and replication. Memory is manageable; serialized operations and network latency drive partitioning.

8. Deep dive 1: Fast partition owners

For N1 and N2, hash the full bucket key onto owners and cache the routing map at gateways. Each owner serializes bucket commands in memory. Refill uses min(capacity, balance + rate × elapsed); fixed-point arithmetic avoids floating-point drift. Batch replication, not deductions, across independent buckets. A single hot bucket remains serialized: load-test its limit and reject excess transport load rather than split its allowance. On owner loss, refresh routing and retry the same request ID; benchmark the extra hop against N1.

9. Deep dive 2: Safe failover

For N3, replicate deductions, deduplication responses, and policy changes through a quorum log before replying. Fence old owners with leadership terms; minority partitions return 503. Persist refill time; across failover, subtract twice the verified clock-error bound from elapsed time, clamping at zero. Freeze refill if clock uncertainty is unbounded. Policy updates enter each bucket's ordered stream: refill under the old policy first, then clamp balance to the new capacity. Responses expose the applied version. This sacrifices availability and some refill during uncertainty rather than inventing tokens.

10. Check the design

N1/N2 map to dive 1; N3 maps to dive 2. Kill an owner after quorum commit but before response: a same-ID retry must return the original decision, and concurrent deductions must not overspend. Measure failover latency separately from healthy p99.
