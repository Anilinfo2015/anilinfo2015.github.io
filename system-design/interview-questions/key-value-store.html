Distributed key-value store

Requirements · Core entities · API or system interface · High-level design · Deep dives

1. Requirements

Functional requirements

Support get, put, and delete on a single opaque key holding opaque bytes; let a request choose its read and write consistency. Operations are single-key only.

Nonfunctional requirements

  1. NFR1: assume 200,000 peak operations/second and values up to 1 MB, with p99 below 10 ms for a single-key get within one region.
  2. NFR2: survive one node and one zone failure with no loss of acknowledged writes, and expose no single point of failure.
  3. NFR3: offer per-request tunable consistency and converge replicas after concurrent or partitioned writes.
  4. NFR4: authenticate every request to a namespace and isolate each tenant's keyspace and quota.

Out of scope

Multi-key transactions, secondary indexes, range scans, and a query language are excluded.

2. Core entities

Key maps to a VersionedValue(bytes, versionVector, tombstone). Partition(tokenRange, replicaSet) assigns each key to N replicas by consistent hashing, and RingMembership(nodeId, virtualTokens, state) tracks the cluster. A delete is a versioned tombstone, never a silent removal, so a late replica cannot resurrect deleted data.

3. API or system interface

PUT /kv/{ns}/{key}?w=W with a body returns 200 {version} once W replicas acknowledge. GET /kv/{ns}/{key}?r=R returns the reconciled value and version, or 404. DELETE /kv/{ns}/{key}?w=W writes a tombstone. Return 503 when fewer than the requested quorum respond, rather than acknowledging a non-durable write. R and W are chosen against the replication factor N; R+W>N gives read-your-writes. Every request is authenticated and scoped to its namespace.

4. High-level design

  1. Any node acts as coordinator: it hashes the key to its N replicas and forwards the operation.
  2. A write waits for W acknowledgements; a read gathers R responses and reconciles them by version.
  3. Gossiped membership keeps the token ring converged as nodes join and leave.

5. Deep dives

Trade-offs and bottlenecks

Consistent hashing with virtual nodes spreads load and limits reshuffling when membership changes, but a hot key still concentrates on one replica set and there is no cross-key transaction. Quorum reads and writes with R+W>N give read-your-writes at higher latency; R=W=1 is fast but may read stale data. Leaderless replication avoids failover stalls but requires conflict resolution, whereas a single leader per partition simplifies conflicts at the cost of failover pauses.

Scale estimate: replica traffic and storage

At 200,000 operations/second with N=3, replicas exchange up to 600,000 messages/second. Assuming 1 KB average values and half writes, write ingress is about 100,000/second times 1 KB times three replicas, roughly 300 MB/second across the cluster. A 100 TB logical dataset stored three times is 300 TB; at 4 TB per node that is about 75 storage nodes before headroom. Using 256 virtual nodes per node keeps the range moved on a single join near one seventy-fifth of the data.

Consistency, conflicts, and repair

Tag each write with a per-key version vector. A read returns the value that dominates; concurrent writes surface as siblings resolved by a physical-timestamp last-writer-wins rule or by an application merge. Heal divergence three ways: read-repair when a stale replica answers, hinted handoff when a replica is briefly unreachable, and background Merkle-tree anti-entropy for durable drift. Garbage-collect tombstones only after a grace period longer than the maximum tolerated replica downtime, or a delete can be undone by a lagging node.

Membership, partitioning, and failure

Nodes gossip ring state and a coordinator routes by token. When a node is lost, its ranges are served by the next replicas and hinted writes replay on its return. A sloppy quorum keeps writes available during partitions but can break R+W>N, so expose it as an explicit lower-consistency mode rather than a silent default. Rebalancing streams only the affected virtual-node ranges to avoid a global reshuffle. Writes fail closed with 503 when W replicas are unreachable, so the store never acknowledges data it cannot make durable.

Check the design

NFR1 maps to in-region quorums; NFR2 to N of at least three across zones with hinted handoff; NFR3 to per-request R and W with version-vector reconciliation; NFR4 to namespace authentication and quotas. Test it by partitioning one replica during a put with W=2 and then reading with R=2: the write must be visible. Kill the coordinator mid-write and retry: the client must not observe a lost acknowledged value.
