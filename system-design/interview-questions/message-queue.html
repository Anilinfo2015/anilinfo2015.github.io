Design a message queue

Requirements · Core entities · API or system interface · High-level design · Deep dives

1. Requirements

Functional requirements

Publish messages; consume and acknowledge messages within a consumer group; inspect or redrive messages that exceed a retry limit. Each group independently consumes retained messages.

Nonfunctional requirements

Assumed targets: N1: publish p99 below 20 ms within one region. N2: support 200,000 messages/s peak with 1 KB payloads. N3: lose zero acknowledged messages after one broker failure and offer at-least-once delivery within a 24-hour retention window.

Preserve append order within a partition, not completion order across concurrently processed messages.

Out of scope

Exclude global ordering, cross-region consensus, and atomic transactions with arbitrary consumer databases.

2. Core entities

Topic has tenant and topic ID. Message uses (topic, partition, offset). ProducerSession uses producer ID and epoch, tracking sequence numbers per partition. Delivery uses (group, partition, offset), with visibility deadline and receipt epoch. The invariant is that committed offsets never refer to messages absent from the replicated log; only the current receipt may acknowledge an active delivery.

3. API or system interface

POST /topics/{id}/messages accepts payload, routing key, producer session, and sequence; returns partition and offset. Same-session, same-sequence retries return the original offset; changed data or expired sessions return 409. POST /groups/{id}/poll takes maximum batch size and wait time, returning messages and receipt tokens. POST /acks accepts those tokens; stale receipts return 409. Tenant ACLs separately authorize publishing, consuming, and redrive. Oversized payloads return 413, quotas 429, quorum loss 503. Dead-letter listing uses cursors; redrive accepts an idempotency key and returns a new message reference.

4. High-level design

flowchart LR
    Producer --> Broker
    Broker --> DurableLog
    Consumer --> Broker
    Broker --> GroupState
    Broker --> DeadLetterQueue
  1. Append a published message and return its durable offset.
  2. Lease eligible messages to polling consumers; acknowledgments mark group delivery complete.
  3. Return expired leases to eligibility, or move exhausted messages to a dead-letter queue for inspection and controlled redrive.

5. Deep dives

Trade-offs and bottlenecks

A database-backed queue simplifies leases but updates hot rows repeatedly. An append-only log amortizes disk writes but needs separate acknowledgment state. Per-message acknowledgments permit parallel workers at greater metadata cost than a sequential consumer offset.

Scale estimate: retained payload and replication

Assume 50,000 messages/s average and fourfold peak. Payload alone is 50 MB/s average, or 4.32 TB per day; three replicas require 12.96 TB for 24 hours before metadata. Peak replication payload is 600 MB/s across all copies. These assumptions require multiple broker disks and partition leaders, not an in-memory queue disguised as durable storage.

Partition throughput

N1/N2 hash routing keys to fixed partitions and distribute leaders across brokers. Batch small appends by bytes or a short flush timer, bounded to preserve the latency budget. Sequential segment writes avoid random payload I/O. Track queue depth and apply tenant byte-rate limits before disks saturate. Hot keys stay on one partition and therefore have a throughput ceiling. On broker failure, clients refresh leader metadata and retry producer sequences. Partition expansion changes key placement, so ordered producers need an explicit drain-and-cutover boundary rather than an invisible rehash.

Durable redelivery

N3 acknowledges publishes after quorum replication and fences leaders by term. Persist producer deduplication state with log entries; reject an expired producer epoch instead of guessing. Group-state shards use (group, partition), recording an acknowledgment bitmap above the contiguous completed offset. Lease expiry schedules redelivery with bounded exponential backoff. A crash after processing but before acknowledgment repeats delivery: consumers must deduplicate business effects. Move exhausted deliveries through a durable outbox so a crash cannot lose the dead-letter copy. Alert before retention expiry; offline groups beyond 24 hours receive an explicit expired-offset error.

Check the design

N1/N2 map to partition throughput; N3 maps to durable redelivery. Kill a broker after quorum append but before replying: a valid producer retry must resolve to the original offset. Kill a consumer before acknowledgment and observe redelivery, not silent disappearance.
