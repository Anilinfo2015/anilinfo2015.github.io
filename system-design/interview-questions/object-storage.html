Object storage

Requirements · Core entities · API or system interface · Data flow · High-level design · Deep dives

1. Requirements

Functional requirements

Create a bucket; store an object, including large ones through multipart upload; read a whole object or a byte range; delete an object; list objects under a key prefix.

Nonfunctional requirements

  1. NFR1: assume 50,000 peak object operations/second and objects up to 5 TB, with first-byte p99 below 100 ms for warm objects.
  2. NFR2: target extreme durability: lose no acknowledged object through multiple disk failures and one zone failure.
  3. NFR3: give read-after-write consistency for a new key and strong consistency for reads after a successful overwrite.
  4. NFR4: enforce bucket ownership and object access rules; serve anonymous reads only through signed, expiring URLs; keep buckets private by default.

Out of scope

In-place random writes, POSIX filesystem semantics, and content indexing or search are excluded.

2. Core entities

Bucket(name, ownerId, policy) contains ObjectVersion(key, versionId, size, etag, manifest, state). A manifest lists Chunk(chunkId, shardLocations) entries, and MultipartUpload(uploadId, parts[]) tracks an in-progress write. An object is immutable once committed; an overwrite creates a new version, and the manifest points only at durable chunks before the key becomes visible.

3. API or system interface

PUT /b/{bucket}/{key} stores a small object. Large objects use POST /b/{bucket}/{key}?uploads to get an uploadId, PUT ...?partNumber&uploadId per part, and POST ...?uploadId to complete with the ordered part list and etags. GET /b/{bucket}/{key} supports a Range header; DELETE versions the removal; GET /b/{bucket}?prefix&continuation lists keys. Errors include 404, 403, 412 on an etag precondition, and 400 for a malformed part list. Signed URLs grant time-boxed, method-scoped anonymous access.

Data flow (optional)

An upload splits into parts; each part is erasure-coded into shards placed across zones; completing the upload commits the manifest, which makes the key visible. A read resolves the manifest, fetches the shards, verifies checksums, and reconstructs the bytes, rebuilding any missing shard from the surviving ones.

4. High-level design

flowchart LR
    Client --> APIGateway
    APIGateway --> MetadataService
    APIGateway --> DataNodes
    MetadataService --> MetadataStore
    DataNodes --> Disks
  1. Upload writes parts to data nodes as erasure-coded shards spread across zones.
  2. Completing the upload commits the manifest in metadata only after enough shards are durable.
  3. A read loads the manifest, fetches shards, and reconstructs the object, repairing on the fly.

5. Deep dives

Trade-offs and bottlenecks

Three-way replication is simple and fast to repair but triples storage; erasure coding such as 10+4 reaches similar durability at about 1.4 times overhead, at the cost of CPU and cross-node reads during repair. A flat key space with prefix listing avoids directory-rename storms but turns listing into a metadata-index problem. Small objects amortize poorly against fixed per-object metadata, so pack them or accept the overhead.

Scale estimate: ingress and node count

At 50,000 operations/second, if a fifth are 5 MB puts, raw ingress is about 10,000 times 5 MB, roughly 50 GB/second, or 70 GB/second after 1.4 times coding, spread across data nodes. One exabyte of logical data at 1.4 times coding is 1.4 EB raw; at 20 TB per node that is about 70,000 data nodes. Multipart parts of 5 MB to 5 GB keep each request independently restartable and parallelize the write across many nodes.

Durability and integrity

Erasure-code each part into k+m shards placed across zones so any m losses are recoverable, and store a checksum per shard verified on every read, triggering reconstruction on a mismatch to catch bit rot. A background scrubber re-reads shards and rebuilds under-protected stripes before further loss. Commit the manifest only after enough shards are durable; an interrupted multipart upload leaves orphaned parts that a sweeper reclaims after a TTL. Deletes are versioned, and lifecycle rules expire old versions on a schedule.

Consistency and access control

Keep object metadata in a strongly consistent, partitioned store keyed by bucket and key, so a completed put is immediately visible for read-after-write. The manifest swap is atomic per key, so an overwrite reader sees either the old or the new version, never a torn mix; listing reads a consistent index, and any index lag only delays appearance in a listing, not a direct get. Authorize every request against the bucket policy, issue short-lived signed URLs bound to method, key, and expiry, and never expose data nodes directly or make buckets public by default.

Check the design

NFR1 maps to parallel multipart and shard fan-out; NFR2 to cross-zone erasure coding with scrubbing; NFR3 to an atomic manifest commit in a consistent metadata store; NFR4 to bucket policy and signed URLs. Test it by failing m shards of a stripe during a get: reconstruction must still return correct bytes and repair the stripe. Interrupt a multipart completion: the key must be either fully visible or absent, never partial.
