Video streaming

Requirements · Core entities · API or system interface · Data flow · High-level design · Deep dives

1. Requirements

Functional requirements

Upload a video; play it at an appropriate bitrate; let owners choose public or private visibility. Private videos use an explicit owner-managed viewer list.

Nonfunctional requirements

  1. NFR1: assume 100,000 concurrent viewers, with p95 playback startup below two seconds on supported broadband connections.
  2. NFR2: target 99.95% monthly playback availability for ready videos.
  3. NFR3: preserve acknowledged finalized uploads through one zone failure.
  4. NFR4: authorize private playback and deny new segment requests within 60 seconds of viewer revocation.

Out of scope

Live broadcasts, recommendations, advertising, DRM, and copyright detection are excluded. Revocation cannot erase bytes a viewer already downloaded.

2. Core entities

Video(videoId, ownerId, visibility, aclVersion, state) references an immutable original. Upload(uploadId) tracks expected size and checksum. Rendition(videoId, generation, bitrate) references a segment manifest. READY means every referenced segment exists and has passed validation; incomplete generations are never published.

3. API or system interface

POST /uploads {bytes, checksum} returns 201 with uploadId and constrained multipart URLs. POST /uploads/{id}/complete {parts} validates ownership, size, and checksums, returning 202 with videoId or 422 for mismatch. Both require Idempotency-Key; matching retries reuse results, changed input returns 409. GET /videos/{id} returns processing state. GET /videos/{id}/playback checks visibility/viewer membership and returns a signed manifest or 409 when not ready. PUT /videos/{id}/access {visibility, viewers, expectedVersion} is owner-only and returns the new version; stale updates return 409. Unauthorized reads return 404.

Data flow (optional)

Multipart upload yields a verified immutable original. Encoding produces bitrate-specific segments; validation precedes publication of a complete manifest. Playback consumes that manifest and selects segments for current bandwidth, with authorization on both manifest and segment requests.

4. High-level design

  1. Reserve an upload, send parts directly to storage, and finalize verified bytes.
  2. A worker produces multiple bitrates and atomically publishes a ready manifest.
  3. Authorize playback, fetch segments through delivery servers, and adapt bitrate to measured bandwidth. Owners update access through the API.

5. Deep dives

Trade-offs and bottlenecks

Pre-encoding costs storage and delays readiness but avoids transcoding during playback. Just-in-time encoding saves rarely watched renditions while risking startup latency. Choose a small pre-encoded bitrate ladder first. The dominant bottleneck is delivery bandwidth, not metadata queries.

Scale estimate: edge delivery and origin headroom

At an average 4 Mb/second per viewer, 100,000 viewers require 400 Gb/second, or 50 GB/second, of peak delivery. A sustained hour transfers 180 TB. With a measured 95% edge byte-hit rate, origins still need 2.5 GB/second. These are payload estimates, excluding protocol overhead; use regional edge delivery and provision origin headroom for cold releases.

Playback capacity and availability

Cache immutable segments by videoId, generation, and rendition. Use short segments and a small initial bitrate to reduce startup downloads. Request coalescing shields origins during popular releases; replicate objects across zones and retry another healthy origin with a bounded deadline. Manifests reference only complete generations, allowing edge nodes to cache segments indefinitely without stale-content ambiguity. Monitor startup latency, rebuffering, and origin saturation separately. A lower starting bitrate trades initial picture quality for speed; multi-region delivery adds storage and transfer costs rather than guaranteeing availability.

Durable publishing and access

Finalize only after the object store confirms cross-zone durability; commit upload state and a processing outbox record together. Workers retry by generation, verify all outputs, and compare-and-set READY. Sweep abandoned uploads and unpublished generations later. Playback authorization reads current ACL state and issues tokens expiring no later than 60 seconds after that check began. Delivery nodes validate tokens on manifests and every segment before cache lookup; private origin objects have no public fallback. ACL failures deny issuance. Replayed completion requests cannot create duplicate videos because request results share the metadata transaction.

Check the design

NFR1–2 map to playback capacity and availability; NFR3–4 map to durable publishing and access. Kill a transcoder halfway through: playback stays unavailable until a complete generation publishes. Revoke a viewer while segments are cached: new segment requests fail after the token bound.
