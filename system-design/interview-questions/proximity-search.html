Design proximity search

Requirements · Core entities · API or system interface · High-level design · Deep dives

1. Requirements

Functional requirements

Publish or move a place; find nearby places; remove a place. Return the closest 100 within a radius, ordered by spherical distance then place ID. Places are public; publishing requires ownership. Over-budget queries return errors, not sampled results.

Nonfunctional requirements

Assumed targets: N1: nearby-query p95 below 150 ms for radii up to 5 km and at most 20,000 candidate records. N2: support five million places and 10,000 queries/s peak. N3: make accepted moves and removals visible within five seconds and prevent older updates from resurrecting removed places after one worker failure.

Out of scope

Exclude travel times, friend tracking, geofencing, and personalized ranking.

2. Core entities

Place uses place ID, with owner, latitude, longitude, category, version, and deletion state. CellEntry uses (cell ID, place ID, version). Mutation uses (place ID, version). The invariant is monotonic place versions: only the current non-deleted record may appear, even if stale entries remain in old cells.

3. API or system interface

PUT /places/{id} accepts coordinates, category, expected version, and request key; returns 202 with the new version. Owner-scoped credentials are required; conflicts return 409, invalid coordinates 400. Same-key write retries return the original version. GET /nearby?lat=&lon=&radius= returns up to 100 IDs, distances, and observed versions, without pagination. Invalid or overly broad queries return 422; throttled client tokens receive 429. DELETE /places/{id} writes an idempotent tombstone. Unauthorized mutations return 403; unavailable complete queries return 503.

4. High-level design

flowchart LR
    Owner --> API
    API --> SpatialDB
    Visitor --> Query
    Query --> SpatialDB
  1. Write versioned coordinates or a tombstone into a database with a spatial index.
  2. Use an index bounding region to select candidates, then calculate exact spherical distances and filter by radius.
  3. Remove deleted entries and sort remaining candidates by distance for the response.

5. Deep dives

Trade-offs and bottlenecks

A spatial database provides consistency, but dense-city scans compete with writes. Spatial cells distribute reads better than hashing places alone. Smaller cells reduce candidates but increase fanout; fixed cell sizes handle uneven density poorly.

Scale estimate: candidate filtering and internal traffic

Five million places at 200 bytes require 1 GB raw, excluding indexes and replicas. At 500 candidates/query, 10,000 peak queries/s means five million distance checks/s, versus 500,000 at an assumed 1,000 average queries/s. Forty-byte candidates produce 200 MB/s peak internal traffic. Co-locate filtering with cell owners and cache stable cell contents.

Spatial partitions

N1/N2 use hierarchical spherical cells, splitting dense cells and grouping sparse ones. Enumerate every cell intersecting the query circle, including neighbors across longitude wraparound; a center-cell-only lookup misses boundary results. Cell owners apply category filters and return candidates. The coordinator batch-validates current place records, computes Haversine distances, and keeps a bounded top-100 heap. Enforce the total candidate budget before returning results. Cache cell membership by generation, not arbitrary rounded user coordinates. Replicate hot cells; if a cell replica fails, retry another within the deadline or return 503 rather than incomplete nearby results.

Moving and deleting places

N3 keeps authoritative places and mutation outboxes together on place-ID shards with quorum commits. A worker adds the new cell entry before removing the old one, using conditional version writes; crashes replay both steps. Queries deduplicate place IDs and validate candidates against current coordinates and tombstones, so stale old-cell entries cannot leak old positions. A moved place can be temporarily absent from its new neighborhood until indexing catches up. Track the oldest unapplied mutation against five seconds and rebuild lost cell indexes from place snapshots plus mutation offsets. Retain tombstones beyond every replay checkpoint.

Check the design

N1/N2 map to spatial partitions; N3 maps to moving and deleting places. Move a place across a cell boundary, crash the worker between writes, then delete it. Both neighborhoods must converge within five seconds, with no duplicated or resurrected result after replay.
