Tag management

Requirements · Core entities · API or system interface · High-level design · Deep dives

1. Requirements

Functional requirements

Create named tags; attach or detach tags on resources; find authorized resources carrying a tag.

Each product supplies a resource-authorization adapter; designing its identity system is unnecessary, but calling it is not optional.

Nonfunctional requirements

  1. NFR1: assume 20,000 peak searches and 2,000 mutations/second, with search p95 below 200 ms.
  2. NFR2: provide immediate authoritative assignment reads after acknowledgement; target search-index convergence within five seconds for 99% of changes.
  3. NFR3: lose no acknowledged assignment after one zone failure.
  4. NFR4: expose zero cross-tenant or unauthorized resource identifiers; check current resource permissions before returning results.

Out of scope

Tag merging, hierarchical taxonomies, full-text search, and analytics are excluded.

2. Core entities

Tag(tenantId, tagId, normalizedName) has a tenant-local unique normalized name. Assignment(tenantId, resourceKey, tagId) is unique, with a mutation version. A resourceKey includes product, type, and id. The invariant is that assignments join resources and tags from the same tenant, without duplicate edges.

3. API or system interface

POST /tags {name} returns 201 with tagId; invalid names return 422 and duplicate names 409. Idempotency-Key retries return the original result; changed payloads return 409. PUT /resources/{key}/tags/{tagId} and DELETE return 204 idempotently after checking resource edit permission and tenant membership. GET /resources/{key}/tags reads authoritative assignments with view permission. GET /tags/{id}/resources?cursor&limit returns up to 100 authorized resources and an opaque cursor. Credentials determine tenant. Inaccessible resources/tags return 404; unavailable authorization returns 503 rather than unfiltered results.

4. High-level design

flowchart LR
    Client --> TagAPI
    TagAPI --> Authorization
    TagAPI --> Database
  1. Normalize names and insert tags under a unique constraint.
  2. Authorize the resource, then insert or delete its assignment transactionally.
  3. Query the reverse assignment index, check each candidate's permissions, and return a bounded page.

5. Deep dives

Trade-offs and bottlenecks

A transactional reverse index makes discovery fresh but hot tags concentrate reads. An asynchronous search index separates query load at the cost of temporarily incomplete results. Choose asynchronous discovery once database measurements justify it, while keeping resource-specific reads authoritative. Permission filtering means some result pages will be short.

Scale estimate: assignment edges and index cost

Assume 100 million resources averaging ten tags: one billion assignment edges. At 80 bytes/edge, raw storage is 80 GB; three copies require 240 GB before indexes. A second reverse index adds substantial storage. At 2,000 peak mutations/second and 200-byte events, index propagation consumes 400 KB/second before replication. Partition edges before introducing a general search engine.

Query partitions and freshness

Partition primary assignments by tenantId plus resource hash. Build reverse-index buckets by tenantId, tagId, and resource hash so a popular tag is not confined to one node. Merge bucket results using deterministic resource-key ordering and authenticated-encrypted per-bucket continuation positions. Versioned outbox events apply only if newer than the indexed state; retain deletion versions against reordered updates. Track publication lag and replay failed events. Confirm candidates against authoritative assignments before returning them; this removes stale deletions, although new assignments can remain absent until indexed. Fan-out and filtering consume the latency budget, so cap work per page.

Durable, authorized mutations

Commit each assignment and its outbox event in the same quorum-replicated transaction. Unique keys make retried attachments harmless; detach retries do not manufacture extra events. Mutation checks bind the caller, tenant, and exact resource operation. Search reads batch-check current permissions before exposing identifiers; never return unfiltered totals or encode raw identifiers in client-readable cursors. Authorization failures fail closed. Encrypt storage and audit permission decisions without logging private resource names. A permission change concurrent with a request follows the authorization service's defined check-time ordering, not an eventual search-index ACL copy.

Check the design

NFR1–2 map to query partitions and freshness; NFR3–4 map to durable, authorized mutations. Stop indexing, detach a resource, then revoke access: search must not return it, authoritative reads reflect the detach immediately, and lag alarms fire before recovery replays the backlog.
