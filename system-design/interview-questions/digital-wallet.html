Digital wallet

Requirements · Core entities · API or system interface · High-level design · Deep dives

1. Requirements

Functional requirements

Hold a balance per user and currency; transfer funds between two wallets; top up from and withdraw to an external funding source; read a balance and a transaction history.

Nonfunctional requirements

  1. NFR1: assume 5,000 peak transfers/second, with acceptance p99 below 300 ms and balance-read p99 below 50 ms.
  2. NFR2: never let a balance go negative or money be created or destroyed; every movement is a balanced double-entry posting.
  3. NFR3: make transfers idempotent by client request id, survive one zone failure for acknowledged transfers, and apply each transfer once.
  4. NFR4: authorize the debit side to the authenticated owner and keep an immutable audit trail for every posting.

Out of scope

Currency exchange, interest, lending or credit, and settlement-bank design are excluded; store provider tokens, never raw funding-instrument details.

2. Core entities

Account(walletId, currency, balanceMinorUnits) holds funds in integer minor units. LedgerEntry(entryId, txnId, accountId, direction, amount) records one leg of a movement, and Transfer(txnId, requestId, from, to, amount, state) ties the legs together. For each transaction the debits equal the credits, a balance equals the sum of its postings, and a requestId is applied once.

3. API or system interface

POST /transfers {fromWallet, toWallet, amount, currency, requestId} returns 201 {txnId, state}; reusing a requestId returns the recorded result, and a different body under the same requestId returns 409. GET /wallets/{id}/balance and GET /wallets/{id}/transactions?cursor read state. Top-ups and withdrawals model the external leg as a pending posting confirmed by a provider callback. Return 422 for insufficient funds and 403 when the caller does not own the debited wallet.

4. High-level design

  1. Validate ownership and available funds for the requested movement.
  2. In one transaction, write the balanced debit and credit postings, update both balances, and record the requestId.
  3. Model an external leg as a pending posting that a provider callback or reconciliation later finalizes or reverses.

5. Deep dives

Trade-offs and bottlenecks

Double-entry inside a single database transaction makes non-negativity and conservation trivial when both accounts share a partition, but a cross-partition transfer needs a distributed commit. One global ledger serializes cleanly yet caps throughput; sharding by account scales but turns most transfers into a two-phase or saga flow. A materialized balance column speeds reads but must update atomically with the postings, or reads drift from the ledger.

Scale estimate: posting volume and idempotency store

Each transfer writes two postings, so 5,000 transfers/second peak is 10,000 postings/second, but sizing storage on a lower average of about 500 transfers/second gives 1,000 postings/second. Over a year that is roughly 31.5 billion postings; at 300 bytes each that is about 9.5 TB raw before replicas and indexes, so keep hot balances in the primary and archive cold postings. Idempotency records retained for 24 hours at peak are about 432 million rows, which the request store must accommodate.

Cross-shard transfers and non-negativity

When both accounts share a partition, post both legs and update both balances in one ACID transaction with a check that the debited balance stays at or above zero. When they live on different partitions, run a two-phase flow: place a hold that debits the source, credit the destination, then release the hold, compensating with a reversing posting on failure. Serialize writes per account with a row lock or a single-writer partition so two concurrent transfers cannot both pass the funds check and overspend. The hold is itself a ledger posting, so the audit trail stays balanced at every step.

Idempotency, durability, and audit

Persist the requestId and its result atomically with the postings, so a retried transfer returns the original outcome and never posts twice. Replicate ledger writes synchronously across zones before acknowledging, and keep the ledger append-only so a correction is a new reversing entry, not an edit. Finalize external legs by an idempotent provider reference, re-querying an unknown outcome rather than assuming it, and run periodic reconciliation that re-sums postings against stored balances to catch drift.

Check the design

NFR1 maps to the single-partition fast path; NFR2 to balanced postings with a non-negative check; NFR3 to a requestId stored atomically with postings plus synchronous cross-zone replication; NFR4 to owner-authorized debits and an immutable log. Test it by firing two concurrent transfers that together exceed the balance: exactly one succeeds. Replay an acknowledged transfer after a zone failover: balances are unchanged and the original txnId is returned.
