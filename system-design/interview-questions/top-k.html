Design a top-k service

1. Requirements

Functional: ingest activity events; return a tenant's top k items; retrieve an item's count. The window spans 60 completed UTC minute buckets, advancing every minute.

Non-functional assumptions: N1: query p95 below 100 ms for k at most 100. N2: accept one million events/s peak across ten million active items. N3: publish each completed-minute view within ten seconds, with exact deduplicated counts for accepted events arriving up to two minutes late, including after one worker failure.

2. Out of scope

Exclude arbitrary windows, unique-user counts, personalized rankings, and corrections beyond two minutes. Counts cover accepted events, not undelivered activity.

3. Core entities

Event uses (tenant, event ID), with immutable item ID and event time. Bucket uses (tenant, item ID, minute). RankingSnapshot uses (tenant, window end, revision). Each accepted event contributes once to one item-owning partition. Ties sort by item ID.

4. API

POST /events accepts authenticated tenant batches and returns per-event acceptance. Same-ID retries are harmless; changed payloads return 409. Invalid or too-late timestamps return 422, overload 429. GET /top?k=&windowEnd= returns item/count pairs, revision, and provisional status; there is no pagination beyond 100. GET /items/{id}/count accepts that revision and returns its count. Reader credentials restrict tenant access; missing retained revisions return 410. Reads are retryable, and counts remain provisional until the lateness allowance closes.

5. Basic design

  1. Insert unique events and increment their minute buckets transactionally.
  2. Every minute, sum the last 60 buckets per item and sort counts for top-k queries.
  3. Store the window revision so ranking and individual count reads use the same view.

6. Trade-offs and bottlenecks

Database sorting repeatedly scans all active items. Heavy-hitter sketches are smaller but introduce cutoff errors and complicate expiration. Choose exact item-owned counts, accepting larger state.

7. Scale estimate

Assume 100,000 events/s average and tenfold peak. One hour contains 360 million events; 24-byte deduplication records alone require 8.64 GB before indexes and replication. Ten million items with 60 eight-byte counters need another 4.8 GB raw. Partition state and enforce retention. With 64 partitions and k=100, a coordinator merges only 6,400 candidates per tenant snapshot rather than ten million items.

8. Deep dive 1: Exact distributed ranking

N1/N2 hash (tenant, item ID) to one owner. Each owner keeps a ring of minute counters and an ordered index by rolling sum; an event or bucket expiry removes the old score and inserts the new score in logarithmic time. Publish each owner's top 100. Their union contains the global top 100 because an omitted item already has 100 better items on its own owner. Merge candidates with a heap and cache the result. Hot-item partial counters must first merge at its owner; ranking independently salted counts is incorrect. Replicas recover query service from the last complete snapshot.

9. Deep dive 2: Windows and replay

N3 deduplicates by tenant/event ID, atomically recording acceptance and an outbox entry before repartitioning by item. Checkpoint bucket state, deduplication progress, and input offsets together. Replay contributes no extra counts. Use event-time buckets with a two-minute watermark delay; publish provisional revisions and corrected revisions for late events. Expose only revisions completed by every partition. If one is missing, retain the older snapshot and expose its age rather than mixing windows. Keep deduplication records beyond the maximum replay and retry horizon.

10. Check the design

N1/N2 map to dive 1; N3 maps to dive 2. Restart a worker mid-checkpoint and replay a duplicated late event: its count must increase once, every returned item must share a revision, and snapshot age must recover within the freshness target.
