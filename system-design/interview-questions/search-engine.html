Design a search engine

Requirements · Core entities · API or system interface · Data flow · High-level design · Deep dives

1. Requirements

Functional requirements

Publish or replace documents; search ranked documents by keywords; delete documents. Assume tenant-wide visibility: any authorized reader in a tenant may search that tenant's documents. Ranking uses lexical relevance rather than personalized recommendations.

Nonfunctional requirements

Assumed targets: N1: search p95 below 200 ms. N2: support 100 million documents and 5,000 searches/s peak. N3: make accepted updates searchable within 60 seconds and lose zero acknowledged source updates after one storage-node failure.

Out of scope

Exclude web crawling, semantic embeddings, document-level access lists, and advertising.

2. Core entities

Document is keyed by (tenant, document ID), with source version and deleted flag. Posting uses (tenant, term, document ID), storing term frequency and positions. Segment has shard ID, generation, and checksum. The invariant is monotonic document versions: replayed older updates cannot overwrite newer content or a tombstone.

3. API or system interface

PUT /documents/{id} accepts text, fields, and expected version; returns 202 with new version or 409 on conflict. A request idempotency key permits safe retries after timeout. DELETE /documents/{id} writes a versioned tombstone with identical retry semantics. GET /search?q=&cursor= returns hits, scores, index generation, and a signed cursor. Tokens restrict tenant and read/write roles; invalid queries return 400, expired cursors 410, overload 429, and unavailable complete results 503. Cursors bind query, tenant, and snapshot and expire after two minutes.

Data flow (optional)

Versioned source mutations become tokens, postings, and searchable index generations; deletions update which documents are live. Queries follow a separate path from analyzed terms to matching postings, comparable scores, and merged ranked hits. Acknowledging a source write and publishing its index generation are distinct events.

  1. Commit source mutations with an outbox row; an indexer consumes them and tokenizes text.
  2. Update term postings or apply a tombstone, then publish a searchable generation.
  3. Analyze query terms, intersect or union posting lists, score matches, and retrieve the highest-ranked documents.

5. Deep dives

Trade-offs and bottlenecks

A relational full-text index is a useful baseline and keeps operations small. Separate immutable index segments scale reads independently but introduce freshness lag and compaction work. Document partitioning distributes storage evenly; term partitioning reduces some query fanout but creates very hot common-term owners.

Scale estimate: index size versus query fanout

At 5 KB per document, 100 million sources require 500 GB raw. Assume measured index size will be roughly 40% of source: budget 200 GB initially, or 600 GB with three copies, then verify on representative text. Forty document shards mean about 5 GB of index each. At 5,000 searches/s, all-shard fanout creates 200,000 shard searches/s, so shard count trades smaller indexes for coordinator and network cost.

Ranking and fanout

N1/N2 use document-ID hashing within tenant shard groups. Each shard intersects sorted postings and uses block-max score bounds to skip candidates that cannot enter its top-k heap. BM25 scoring shares versioned corpus statistics across the group so local scores are comparable. Merge each shard's top k with deterministic document-ID tie-breaking. Cache common query results by snapshot; replicate hot groups rather than blindly adding shards. A failed replica is retried within the request deadline. If any shard remains unavailable, return 503 instead of silently presenting incomplete rankings.

Recoverable publication

N3 puts source rows and outbox records in the same quorum-replicated shard transaction. Indexers process each document's versions monotonically, build immutable segments, verify checksums, and atomically publish manifests. Checkpoint offsets only after publication; replay after crashes ignores older versions. Deletes enter a live-document bitmap before later compaction removes postings. Keep tombstones until all older segments and replay checkpoints are retired. Monitor oldest unpublished mutation age and reserve indexing capacity separately from search. Recover corrupt segments from source plus log; source acknowledgment does not imply immediate search visibility.

Check the design

N1/N2 map to ranking and fanout; N3 maps to recoverable publication. Crash an indexer during manifest publication, then replay a pre-delete update: readers must see a complete generation, and the deleted version must not reappear. Measure catch-up against 60 seconds.
