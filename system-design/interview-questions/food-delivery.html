Food delivery

1. Requirements

Functional: place a priced food order; let restaurants and couriers advance fulfillment; let customers track order status.

  1. NFR1: assume 2,000 peak placements/second; target order-acceptance API p95 below 500 ms, excluding asynchronous payment-provider work.
  2. NFR2: charge at most the accepted integer-minor-unit total once per order; prevent invalid fulfillment transitions.
  3. NFR3: preserve acknowledged orders through one zone failure and target 99.9% monthly status availability.
  4. NFR4: expose addresses only to the customer, fulfilling restaurant, and assigned courier; revoke courier access within five seconds of reassignment.

2. Out of scope

Menu search, courier optimization, promotions, tips, and post-pickup cancellations are excluded. A provider supplies tokenized authorization, capture, void, and refunds; raw card data never enters this service.

3. Core entities

Quote(quoteId, customerId, restaurantId, lines, totalMinor, currency, expiresAt) snapshots prices. Order(orderId, state, version) references that quote and delivery address. PaymentStep(orderId, action) records provider identity/status. Assignment(orderId, courierId) controls delivery access. Payment state and fulfillment state are separate; an order cannot become PREPARING without confirmed capture.

4. API

POST /orders {quoteId, addressId, paymentToken} requires customer authentication and Idempotency-Key, returning 202 {orderId, state: PENDING_PAYMENT}. Retries reuse the order; changed input returns 409, invalid quote/address 422. POST /orders/{id}/transitions {action, expectedVersion, requestId} returns new state or 409. Order owners cancel before pickup; restaurant staff accept/reject/mark ready; assigned couriers mark pickup/delivery. Internal PUT /orders/{id}/assignment {courierId, expectedVersion, requestId} is dispatch-service-only before pickup, returning the version or 409. GET /orders/{id} returns role-filtered data, or 404 for unauthorized callers. Persist mutation results for safe retries.

5. Basic design

flowchart LR
    Customer --> OrderAPI
    Restaurant --> OrderAPI
    Courier --> OrderAPI
    Dispatch --> OrderAPI
    OrderAPI --> Database
    Database --> Worker
    Worker --> PaymentProvider
  1. Validate the quote and address; commit the order and authorization task.
  2. Authorize funds, obtain restaurant acceptance, then capture before permitting preparation. Rejection triggers a void.
  3. Dispatch selects an available courier and commits assignment. Record readiness, pickup, and delivery; serve role-filtered status.

6. Trade-offs and bottlenecks

Database transactions cannot include restaurant decisions or remote payments. Use a persisted workflow with pending states and compensations. Authorizing before acceptance ties up funds temporarily, but capturing afterward reduces refunds for rejected orders.

7. Scale estimate

Assume two million orders/day: about 23 placements/second average, far below the 2,000 peak. Twelve 500-byte workflow events/order produce 12 GB/day raw, or 36 GB with three copies before indexes. One million active customers polling every five seconds create 200,000 status reads/second. Push status changes and use brief versioned status caches; keep address authorization outside shared caches.

8. Deep dive 1: Fast, durable order state

Partition orders by orderId and quorum-replicate state, request results, and outbox events together. Return 202 after commit, not payment. Workers claim leased tasks with bounded retries; replay compares expectedVersion before changing state. Versioned caches serve non-sensitive status; authorization remains authoritative. Push gateways reduce polling; GET remains the recovery path. Dead-letter tasks page operators rather than abandoning orders. Per-restaurant admission limits bound overloaded kitchens' pending queues.

9. Deep dive 2: Payment recovery and address access

Derive stable provider keys from orderId and action; store intent before calling. After a timeout, query that operation or retry its same key, never issue a fresh capture. Deduplicate signed callbacks. Beyond provider idempotency retention, unresolved operations require lookup/manual reconciliation, not another charge. If cancellation wins while capture is uncertain, enter CANCEL_PENDING; confirm capture then refund, or establish terminal non-capture then void. Refunds have stable identities. State guards prevent new capture intents after cancellation and preparation before payment. Address reads verify current role/assignment; courier capabilities last at most five seconds. Authorization outages fail closed; push payloads and logs omit addresses.

10. Check the design

NFR1,3 → dive 1; NFR2,4 → dive 2. Drop a successful capture response and retry placement: one order and one capture remain. Reassign the courier during recovery: the old courier loses address access within five seconds.
