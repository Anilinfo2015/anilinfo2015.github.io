Distributed cache

Requirements · Core entities · API or system interface · High-level design · Deep dives

1. Requirements

Functional requirements

Read a key; set a value with a TTL; delete a key.

Nonfunctional requirements

  1. NFR1: assume 100,000 peak operations/second, values at most 64 KB, and same-region p95 below 5 ms.
  2. NFR2: target linearizable operations per key, including across leader failover; eviction may turn any value into a miss.
  3. NFR3: target 99.9% monthly availability through one node failure.
  4. NFR4: permit zero cross-tenant reads or writes and enforce a configured memory quota per tenant.

Out of scope

Cross-key transactions, database persistence guarantees, and automatic source-database invalidation are excluded. Applications must tolerate cache misses and prevent stale database reads from repopulating invalidated entries.

2. Core entities

Entry(tenantId, key) contains bytes, a version, and expiresAt. Shard(shardId) tracks replicas and leader epoch. Request(tenantId, requestId) records recent mutations. The invariant is that a read never returns another tenant's bytes or a value already expired at its linearization point.

3. API or system interface

GET /cache/{key} returns 200 with bytes/version or 404 for a miss. PUT accepts bytes, TTL of 1–86,400 seconds, and optional expectedVersion; it returns the new version. DELETE returns 204. Credentials select tenant and read/write permissions. Mutations require requestId: identical retries within ten minutes return the original result without extending TTL; changed payloads return 409. Version mismatches, including a missing expected entry, return 409; oversized values return 413, quotas 429, unavailable quorum 503. After the retry window, resolve uncertainty with GET rather than replaying an old mutation.

4. High-level design

flowchart LR
    Client --> Gateway
    Gateway --> CacheNode
    CacheNode --> Memory
  1. Authenticate, validate size/TTL, and namespace the key.
  2. Serialize reads and mutations on that key; check expiry during reads.
  3. Apply deletes and reclaim expired or evicted entries.

5. Deep dives

Trade-offs and bottlenecks

A single memory node gives simple ordering but loses service on failure. Client-side sharding saves a gateway hop but complicates credential enforcement and topology changes. Keep gateways initially. Strict per-key ordering costs more than asynchronous replicas, but avoids resurrecting a recently deleted value after failover.

Scale estimate: shard capacity and memory headroom

Assume 20 million live entries averaging 1 KB payload plus 100 bytes metadata: 22 GB raw using decimal units. Three copies consume 66 GB before allocator overhead. Eight shards average 12,500 operations/second at peak, but one hot key can dominate a shard. Choose shard counts from measured single-shard latency and reserve at least 30% memory headroom.

Partitioning and tenant protection

Hash tenantId plus key into movable shards. Gateways derive tenant identity from credentials; storage nodes also validate signed internal tenant context. Charge payload, metadata, and deduplication records to tenant budgets; use per-tenant admission limits and eviction so a noisy tenant cannot consume all memory. Serve hot reads only from the owning leader; coalescing concurrent reads reduces pressure without weakening consistency. Large values need stricter bandwidth limits. This addresses latency and isolation, but a single hot key remains a scaling boundary.

Ordered failover and expiry

Three cross-zone replicas maintain a consensus log. Writes require quorum; reads need a valid leader lease or quorum confirmation. Before returning an expiry miss, quorum-commit a tombstone conditional on the observed version; retry reads on conflict. Replicate deletions, evictions, and request results too. Preserve versions through expiration and snapshots; subsequent PUTs receive strictly newer versions. Transfer snapshot plus log and fence old owners during rebalancing. Monitor clock skew for TTL accuracy; suspend serving beyond its configured bound. Clock checks alone cannot prevent resurrection. Minority partitions return 503. Replication adds memory and network costs; benchmark the five-millisecond goal.

Check the design

NFR1,4 map to partitioning and tenant protection; NFR2–3 map to ordered failover and expiry. Expire a key, return a miss, then promote a replica with a slower clock: reads remain misses and recreation has a newer version. Another tenant's identical textual key remains unaffected.
