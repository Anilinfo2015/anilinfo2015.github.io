Collaborative editor

1. Requirements

Functional: create and share a text document; edit it concurrently; reconnect and synchronize offline edits.

  1. NFR1: assume 10,000 active documents, at most 100 simultaneous editors/document, and same-region remote-edit p95 below 150 ms.
  2. NFR2: replicas receiving the same accepted operations must converge; acknowledged operations survive one zone failure.
  3. NFR3: support automatic synchronization for clients offline up to 24 hours without silently discarding local edits.
  4. NFR4: accept operations only from current editors and stop removed members receiving new remote content within five seconds.

2. Out of scope

Rich text, spreadsheets, and cross-document transactions are excluded. Limit visible text to 1 MB. Clients offline beyond 24 hours retain local copies but may need reconciliation.

3. Core entities

Document(docId, ownerId, epoch) owns grants and snapshots. RGA text atoms have immutable (LamportCounter, actorId) identifiers; insertions reference predecessors and deletions tombstone identifiers. Operation(docId, actorId, counter) is unique. Snapshots retain causal metadata/tombstones. Accepted operations never reuse identities with different content.

4. API

POST /documents {title} uses Idempotency-Key and returns docId; changed retry input returns 409. PUT /documents/{id}/members/{userId} {role} is owner-only and idempotent. GET /documents/{id}/snapshot requires read permission and returns epoch/state/cursor. An authenticated WebSocket accepts sync {epoch, cursor} and apply {actorId, counter, dependencies, operations}; durable acknowledgement returns the operation identity and log cursor. Actor identities are bound to the principal. Duplicate operations return their recorded acknowledgement; changed payloads return 409, invalid operations 422, obsolete epochs 410, revoked access 403. Backlog retrieval uses bounded cursor pages.

5. Basic design

  1. Create a document and grants, then load its snapshot.
  2. Apply local edits optimistically; validate and append operations server-side before acknowledgement and broadcast.
  3. Reconnect, fetch missing operations, and resend unacknowledged local operations using stable identities.

6. Trade-offs and bottlenecks

Operational transformation uses smaller operations but ties offline rebasing to server history. Choose RGA: traverse predecessor subtrees with siblings ordered by descending (LamportCounter, actorId); tombstones retain insertion anchors. Buffer missing dependencies; advance counters beyond observed timestamps. Stable identities handle duplicates, but tombstones enlarge snapshots.

7. Scale estimate

Assume ten active editors/document each producing two batched operations/second: 200,000 operations/second overall. At 200 bytes/operation, raw log ingress is 40 MB/second, or 3.456 TB/day if sustained. Three copies consume 10.368 TB/day before indexes. Average per-document delivery is 20 operations/second to ten clients; fan-out capacity matters separately. Batch keystrokes and compact snapshots rather than retaining an unbounded replay log.

8. Deep dive 1: Document-local ordering and convergence

Hash docId to a fenced owner and a cross-zone replicated log. Serialize admission per document, validate dependencies, and acknowledge only quorum-committed operations; clients buffer dependency gaps. Broadcast after commit. Receivers merge CRDT operations deterministically and deduplicate by identity; a log cursor simplifies replay but does not replace CRDT identifiers. A hot document cannot be split arbitrarily without coordinating edits, so cap participants and queue depth. Batch nearby operations for a few milliseconds, then measure end-to-end latency. On failover, reload snapshot plus committed tail; optimistic edits without acknowledgements remain visibly pending.

9. Deep dive 2: Offline retention and membership

Retain operation identities, causal metadata, and deletion tombstones for at least the 24-hour offline window, with recovery margin. Compact only past registered clients' safe frontiers; retire expired clients through an epoch transition. An obsolete client receives a new snapshot and keeps its unsynchronized branch for explicit reconciliation, never a misleading success. Check current editor grants at durable admission, so previously authorized offline edits can be rejected after removal. Streaming readers use five-second authorization leases and stop on expiry without renewal. Keep snapshots private and encrypt storage. More retention improves offline recovery but directly increases storage and merge costs.

10. Check the design

NFR1–2 → dive 1; NFR3–4 → dive 2. Disconnect two editors, edit concurrently, reconnect, and kill the owner after commit: replicas converge, acknowledged edits persist, and a removed editor's replay is rejected.
