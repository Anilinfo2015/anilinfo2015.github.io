--- title: "URL shortener: an interview design" description: "Immutable short links, fast redirects, and bounded revocation." ---

URL shortener

1. Requirements

Functional: create a short link; redirect a visitor; let its owner disable it.

  1. NFR1: assume 50,000 peak redirects/second with server-side p95 below 50 ms.
  2. NFR2: target 99.95% monthly redirect availability.
  3. NFR3: never assign one alias to two destinations; preserve acknowledged creates through one availability-zone failure.
  4. NFR4: allow only owner mutations and stop redirects within five seconds of acknowledged disabling.

2. Out of scope

Custom domains, editable destinations, analytics, and destination-content moderation are excluded. Links are public bearer references, not access controls for destination content.

3. Core entities

Link(alias PK, ownerId, destination, state, expiresAt) has an immutable destination. CreateRequest(ownerId, requestId) stores the request hash and resulting alias. Retain disabled aliases as tombstones: an old printed link must never point to a new owner.

4. API

POST /links {destination, expiresAt} requires authentication and an Idempotency-Key; it returns 201 {alias, shortUrl}. Accept only HTTP(S) URLs; invalid input returns 422. Reusing a key with different input returns 409; matching retries return the recorded result. GET /{alias} returns 302 with Location, 404 if unknown, or 410 if disabled/expired. DELETE /links/{alias} checks ownership, returns 204 on repeated disabling, and 403 for another owner. Redirect responses use Cache-Control: no-store.

5. Basic design

flowchart LR
    Visitor --> App
    Owner --> App
    App --> Database
  1. Create a random alias and atomically insert its link and idempotency record.
  2. Read the link by alias, check state and expiry, then redirect.
  3. Disable the owner's link transactionally; retain its identity.

6. Trade-offs and bottlenecks

A relational unique index makes collision handling straightforward, but every redirect hits storage. Sequential identifiers avoid random collisions yet reveal creation order. Random 96-bit identifiers are less enumerable; uniqueness still comes from insertion, not probability. Retry generation on conflict.

7. Scale estimate

Assume one million creations/day and ten million average redirects/hour: about 2,778 redirects/second, versus the 50,000 peak. At 300 bytes/link, one year adds 109.5 GB raw; three replicas need 328.5 GB before indexes. A 99% application-cache hit rate would reduce peak database reads to 500/second. Measure that hit rate before choosing storage shards.

8. Deep dive 1: Fast redirects during failures

Use regional application caches keyed by alias and replicated database readers. Coalesce concurrent misses for hot links, and cap negative-cache lifetimes to avoid hiding newly created aliases. Independently scale stateless redirect workers; use timeouts and admission limits rather than unlimited database retries. Cache entries expire at the earlier of link expiry or five seconds after the authoritative read began. Check this freshness deadline before emitting any redirect, including cache misses. This sacrifices some outage availability for revocation correctness; load and zone-failure tests must establish whether the availability target remains realistic.

9. Deep dive 2: Durable identity and revocation

Route creates and disables to a leader with synchronous cross-zone quorum commits. Cache fills use authoritative reads, not lagging replicas. The uniqueness constraint and request record commit together, so a lost response can be retried without making another link. Ownership comes from the authenticated principal, never a supplied owner field. Disabling emits invalidations as an optimization; the five-second freshness bound handles lost events. On unavailable authority, expired entries fail closed with 503. Store backups separately; tombstone retention incurs permanent metadata cost.

10. Check the design

NFR1–2 → dive 1; NFR3–4 → dive 2. Test a dropped disable-invalidation event followed by leader failure: no redirect may succeed after the five-second boundary, and retrying an acknowledged create must return its original alias.
