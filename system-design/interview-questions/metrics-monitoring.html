Design metrics monitoring

Requirements · Core entities · API or system interface · Data flow · High-level design · Deep dives

1. Requirements

Functional requirements

Ingest timestamped metrics; query charts over time ranges; configure threshold alerts and inspect their state. Support gauges and monotonically increasing counters with explicit reset handling.

Nonfunctional requirements

Assumed targets: N1: ingest one million samples/s peak and expose accepted samples within ten seconds. N2: chart queries over at most 1,000 series and 24 hours finish below two seconds p95. N3: detect sustained threshold breaches within 60 seconds and preserve acknowledged samples through one storage-node failure.

Retain raw metrics for seven days and minute rollups for 90 days.

Out of scope

Exclude logs, distributed traces, arbitrary joins, and notification-provider design.

2. Core entities

Series uses a collision-checked hash of tenant, metric name, and canonical labels. Sample uses (series ID, timestamp), with value. AlertRule uses (tenant, rule ID); Evaluation uses (rule ID, evaluation time). The invariant is one canonical value per sample key: identical retries are harmless, conflicting values are rejected rather than silently summed.

3. API or system interface

POST /samples accepts labeled batches and returns per-sample acceptance or errors. Tenant-scoped agent tokens authorize writes; retries resend only unacknowledged samples. Invalid timestamps return 400, conflicting samples 409, and cardinality or throughput limits 429 with Retry-After. GET /query accepts expression, start, end, and step; returns bounded series arrays or 422 for excessive cost. Reader tokens cannot cross tenant boundaries. PUT /alerts/{id} takes expression, threshold, duration, and expected version; returns version or 409. GET /alerts/{id} returns active, inactive, or unknown state.

Data flow (optional)

Labeled samples become canonical series points, recent queryable data, and compressed blocks with minute rollups. Chart queries select series and time ranges; alert evaluations turn sampled values into durable state transitions, treating missing data separately from healthy values.

5. Deep dives

Trade-offs and bottlenecks

A general database handles small deployments but high-cardinality indexes and continuous writes compete with scans. Compressed time-series blocks reduce storage and scan costs; delayed block sealing requires a separate recent-data path. Approximate sketches would save space for distributions but cannot replace exact gauge histories.

Scale estimate: compression and retention

Assume 500,000 samples/s average, twice that at peak, and 16 raw bytes per timestamp/value pair. Raw payload is 8 MB/s, or 691.2 GB/day; seven days need 4.84 TB, before labels and replicas. Three copies approach 14.5 TB. This justifies compression, explicit retention, and rollups rather than keeping all samples in query-process memory.

Ingest and query partitions

N1/N2 partition by tenant and series hash, then time. Series owners serialize compare-and-append by sample key: identical values reuse acceptance, conflicts return 409, and new values require quorum commit before acknowledgment. The comparison covers buffered and persisted samples. Rebuild buffers from log offsets after crashes; merge reads by sample key. Label indexes narrow scans; quotas bound cardinality. Minute rollups retain count, sum, minimum, and maximum; counter rates use reset-aware deltas. Bound output points, use coarser rollups for long ranges, and reject expensive queries to protect ingestion.

Alert correctness

N3 acknowledges only quorum-durable sample writes. Assign rules by tenant/rule hash with renewable leases and fenced evaluation epochs. Evaluate every 15 seconds after a ten-second ingestion allowance; a configured 30-second sustained breach therefore targets detection within 60 seconds. Persist pending-since time, evaluation watermark, and transition outbox atomically. After failover, replay missing evaluation slots; a unique transition key suppresses duplicate notifications locally. Missing data produces unknown, not healthy. Older late samples may correct charts but do not retract already-sent alerts; display that policy explicitly.

Check the design

N1/N2 map to ingest and query partitions; N3 maps to alert correctness and quorum-durable ingestion. Race conflicting samples, then kill their storage leader: only one value may succeed and survive. Kill an evaluator after transition commit: its replacement must preserve pending duration and reuse the transition key.
