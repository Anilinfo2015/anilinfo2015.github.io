--- title: "Leaderboard: an interview design" description: "Real-time ranked scores with exact rank and idempotent updates." ---

Leaderboard

Requirements · Core entities · API or system interface · High-level design · Deep dives

1. Requirements

Functional requirements

Record a player's score change; read a player's score and rank; read the top N; read a window of players around a given player. Scope the design to one leaderboard, such as a game mode, with periodic resets.

Nonfunctional requirements

  1. NFR1: assume 100,000 score updates/second and 50,000 rank reads/second, with p99 below 100 ms for top-N and for a player's own rank.
  2. NFR2: reflect an update in ranks within two seconds for 99% of updates, with deterministic tie-breaking so ordering is exact.
  3. NFR3: preserve acknowledged score events through one zone failure and apply each event once, so a retry never double-counts.
  4. NFR4: authorize score writes to the owning player or service and validate deltas to resist tampering.

Out of scope

Anti-cheat modeling, aggregation across leaderboards, and historical replay beyond the current period are excluded.

2. Core entities

Leaderboard(id, period, resetAt) holds many Score(playerId, value, updatedAt) rows, ordered by a sorted structure. ScoreEvent(eventId, delta) records each change for idempotency. Rank is derived from the sorted order of (value, tiebreak), and an eventId is applied at most once.

3. API or system interface

POST /leaderboards/{id}/scores {playerId, delta, eventId} returns 200 {value}; reusing an eventId with a different delta returns 409, and a matching retry returns the recorded value. GET /leaderboards/{id}/top?n returns an ordered list, GET /leaderboards/{id}/players/{playerId} returns {value, rank}, and GET /leaderboards/{id}/around/{playerId}?k returns the neighbours above and below. Writes require an authorized principal and a validated delta.

4. High-level design

flowchart LR
    Client --> ScoreService
    ScoreService --> EventLog
    ScoreService --> SortedStore
    RankService --> SortedStore
  1. A score write is deduplicated by eventId, appended to a log, and applied to the sorted structure.
  2. Top-N and around-me queries read the sorted structure directly.
  3. An order-statistics index answers an arbitrary player's exact rank.

5. Deep dives

Trade-offs and bottlenecks

A sorted set backed by a skip list or balanced tree gives O(log N) updates and O(log N + n) top-N and supports rank queries, but a single instance caps throughput and one hot leaderboard is the scaling unit. Exact rank for an arbitrary player is the costly part: an order-statistics tree answers it in O(log N), while periodic snapshot ranking is cheaper but stale. Sharding by score range parallelizes writes but turns global rank into a cross-shard sum.

Scale estimate: update cost and memory

At 100,000 updates/second, a skip-list update over ten million players is about 23 comparisons, so CPU is cheap and single-writer contention is the real limit; partition by leaderboard and replicate hot ones. A top-100 read touches 100 entries, so 50,000 reads/second is about five million element reads/second served from memory. Ten million players at roughly 64 bytes each is about 640 MB per leaderboard, small enough to keep resident.

Exact rank at scale

Keep an in-memory order-statistics structure per leaderboard so rank and around-me are O(log N). To exceed one machine, shard by score bucket: each shard holds a local sorted set and a count, and a player's global rank is the players above them in their own shard plus the summed counts of all higher-scoring shards, read from a small per-shard count index. Break ties by value descending, then earliest updatedAt, then playerId, so ordering is deterministic and reproducible after failover.

Durability, idempotency, and reset

Append every accepted ScoreEvent to a replicated log keyed by eventId before touching the in-memory structure; on restart, rebuild from the latest snapshot plus the log tail. Deduplicate by eventId so client retries and at-least-once delivery cannot double-count. A period reset rolls to a new period id, snapshots the old period immutably for read-only access, and starts the new one empty. A zone failure fails over to a replica built from the same log, preserving order.

Check the design

NFR1 maps to an in-memory sorted set, partitioned; NFR2 to a synchronous structure update after the log append; NFR3 to the replicated event log with eventId dedup; NFR4 to authorized, validated deltas. Test it by submitting the same eventId twice across a failover: the score rises once and the duplicate does not change rank. Kill the primary after the log append but before the in-memory update: the replica must show the score after replay.
