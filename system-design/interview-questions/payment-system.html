Design a payment system

1. Requirements

Functional: create and capture a payment; refund a captured payment; retrieve payment and refund status. Assume one currency per payment and a processor that supports merchant-scoped idempotency keys.

Non-functional assumptions: N1: command acceptance p99 below 300 ms, excluding processor completion. N2: sustain 2,000 commands/s peak. N3: zero unbalanced ledger transactions or internally accepted over-refunds. N4: lose zero acknowledged commands after one storage-node failure and reconcile unknown processor outcomes within 15 minutes while its query API is healthy.

2. Out of scope

Exclude card vaulting, foreign exchange, lending, fraud-model design, and settlement banking. Store processor tokens, never raw card details.

3. Core entities

Payment uses (merchant ID, payment ID), with amount in integer minor units and currency. Refund references a payment. Command is unique by (merchant, idempotency key). LedgerTransaction owns entries keyed by (transaction ID, line number). Every posted transaction balances debits and credits within one currency; successful plus reserved refunds never exceed captured value.

4. API

POST /payments accepts amount, currency, processor token, and idempotency key; returns 202 with payment ID and pending status. POST /payments/{id}/refunds accepts amount and a new key, returning refund ID. Merchant credentials must own the payment; refund permission is separate. Invalid amounts return 400, changed payloads under an existing key or excess refunds 409, throttling 429. Retry uncertain submissions with the same key; retained command records preserve the original response. GET /payments/{id} returns state, captured/refunded amounts, and cursor-paginated refunds.

5. Basic design

    Merchant --> API
    API --> Database
    Worker --> Database
    Worker --> Processor
    Processor --> Webhook
    Webhook --> Database
  1. Validate the merchant and save a payment command with an outbox entry in one transaction.
  2. A worker submits capture or refund with the command's stable processor key.
  3. Apply verified processor results transactionally to payment state and balanced ledger entries; status reads use these records.

6. Trade-offs and bottlenecks

A single SQL ledger simplifies balance checks and investigation. Direct synchronous processor calls avoid a queue but cannot atomically commit local state with an external charge. Durable asynchronous commands make that uncertainty explicit; users must tolerate pending states.

7. Scale estimate

Assume 200 commands/s average, tenfold peak, and four 200-byte ledger entries per completed command. The upper-bound raw entry rate is 160 KB/s average, or 13.8 GB/day. Three replicas need about 41.5 GB/day before indexes. Retain immutable history in partitioned storage; shard active processing rather than repeatedly scanning the full ledger.

8. Deep dive 1: Local transaction boundaries

N1–N3 use merchant-hash shards, keeping payment commands, refund reservations, and ledger entries together. Acceptance commits only local work; processor calls run outside locks. Lock the payment row to reserve refundable value before enqueueing; concurrent refunds therefore cannot both spend it. Release reservations only after definitive failure. A posting procedure validates equal debit and credit sums and uses a unique external-operation ID. Worker crashes replay commands, but unique command/posting constraints suppress repeated local effects. Very large merchants need dedicated shards; splitting their ledger requires a new transaction boundary.

9. Deep dive 2: Resolving uncertainty

N4 requires quorum commits before acknowledgment and a transactional outbox on each merchant shard. A timeout moves the operation to unknown, not failed. Query the processor using the stable operation reference; retry only within its documented idempotency retention window. Beyond that window, quarantine for reconciliation rather than risk another charge. Partition reconciliation scans by merchant shard and next-check time, using leased batches and jittered retries. Signed webhooks and polling enter the same deduplicating state machine. Reconcile processor statements against ledger postings; record corrections as new balanced transactions, never edits.

10. Check the design

N1–N3 map to dive 1; N4 maps to dive 2. Kill a worker after processor capture but before local commit: status should become unknown then captured through reconciliation, with one local posting and no second capture.
