Design a notification service

Requirements · Core entities · API or system interface · High-level design · Deep dives

1. Requirements

Functional requirements

Submit email or push notifications; manage recipient channel preferences; inspect delivery status. Each request targets one recipient, with optional fallback from push to email.

Nonfunctional requirements

Assumed targets: N1: acceptance p99 below 200 ms. N2: submit 10 million notifications/day with a tenfold peak. N3: 99% of eligible intents reach a provider within 60 seconds while that provider is healthy. N4: lose zero acknowledged intents after one database-node failure.

Out of scope

Exclude campaign audience selection, template editing, inbox rendering, and guaranteed human receipt. A provider's acceptance is not evidence that a person read a message.

2. Core entities

Intent has notification ID, tenant, recipient, content reference, and idempotency key. Preference is keyed by (tenant, recipient, channel). Attempt uses (notification ID, channel, attempt number); an outbox row references the intent. The invariant is one logical intent per tenant idempotency key and a recorded outcome for every completed attempt.

3. API or system interface

POST /notifications accepts recipient, template variables, allowed channels, and idempotency key; returns 202 with notification ID. A same-key retry returns that ID; different content returns 409. Tenant-scoped service credentials must authorize the recipient namespace and template. Invalid input returns 400; admission throttling returns 429 with Retry-After. PUT /preferences accepts channel settings and expected version, returning the new version or 409; users may change only their own preferences. GET /notifications/{id} returns authorized status and a cursor-paginated attempt history.

4. High-level design

flowchart LR
    Client --> API
    API --> Database
    Worker --> Database
    Worker --> Provider
    Provider --> Callback
    Callback --> Database
  1. Atomically create the intent and outbox row; preferences and status reads use the same database.
  2. A polling worker checks current preferences, records an attempt, and calls the selected provider.
  3. Record acceptance or failure; try an allowed fallback after definitive failure. Signed provider callbacks update delivery status.

5. Deep dives

Trade-offs and bottlenecks

Synchronous provider calls would simplify status reporting but couple API latency to provider outages. An outbox adds background work and eventual status changes, while keeping acceptance independent. The baseline polling table eventually contends with user-facing reads.

Scale estimate: intent retention and provider capacity

Ten million/day is about 116 intents/s average and 1,160/s peak. At 1 KB per intent, retain 10 GB raw/day, excluding payload objects and attempts. Three replicas require 30 GB/day before indexes. Separate payload storage and expire detailed attempts after the agreed retention period; provision workers against peak provider throughput rather than the daily average.

Scheduling delivery

N1–N3 use an outbox relay and channel-specific queues partitioned by tenant and recipient hash. Weighted fair queues prevent a large tenant starving others; token buckets enforce provider quotas. Workers use exponential backoff with jitter and a delayed-retry heap, leaving ready work unblocked. Lease expiry recovers crashed workers. Check preferences immediately before dispatch; suppression is terminal, although an already-dispatched message cannot be recalled. Track oldest eligible intent age and shed new traffic with 429 when healthy-provider capacity cannot meet N3.

Durable outcomes

N4 requires quorum-replicated intent/outbox commits before 202. Derive notification ID and shard deterministically from (tenant, idempotency key); enforce full-key uniqueness there, keeping intent and outbox together. Relays mark progress only after durable enqueue; workers claim attempts conditionally to tolerate duplicate enqueue. Pass stable provider idempotency keys where supported. After an ambiguous timeout, query provider status before retrying or falling back. Without provider deduplication, delivery can duplicate; expose an unknown outcome instead of asserting single delivery. Authenticate callbacks, deduplicate event IDs, and reject state regressions from delayed callbacks.

Check the design

N1–N3 map to scheduling delivery; N4 maps to durable outcomes. Crash the relay after enqueue but before marking its row: the intent must remain traceable, duplicate work must converge, and a provider outage must not block healthy-channel queues.
