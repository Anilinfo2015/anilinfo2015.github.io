Maps and routing

Requirements · Core entities · API or system interface · Data flow · High-level design · Deep dives

1. Requirements

Functional requirements

Given an origin and destination, return a driving route with distance and estimated time; render map tiles for a viewport; recompute a route when the driver deviates.

Nonfunctional requirements

  1. NFR1: assume 20,000 peak route requests/second, with route p99 below 300 ms for intra-metro trips and tile p99 below 50 ms.
  2. NFR2: reflect major closures and traffic in estimates within a few minutes, and return only valid routes that respect connectivity and turn restrictions.
  3. NFR3: keep serving tiles and routes through one zone failure, degrading to traffic-free estimates rather than failing.
  4. NFR4: enforce per-key quotas and do not retain an individual user's trajectory beyond the request without consent.

Out of scope

Turn-by-turn voice guidance, indoor maps, map-data licensing, and multi-modal transit routing are excluded.

2. Core entities

RoadGraph(nodeId, edges[weight, restrictions]) is a directed graph with turn rules. Tile(z, x, y, blob) is a pre-rendered map image, TrafficOverlay(edgeId, speed, asOf) is a time-varying weight layer, and RouteResult(geometry, distanceM, etaS, steps) is the answer. Traffic is an overlay on edge weights, not a change to the graph topology.

3. API or system interface

GET /route?from=lat,lng&to=lat,lng&depart=now returns {geometry, distanceM, etaS, steps}. GET /tiles/{z}/{x}/{y}.pbf returns a vector tile. Return 400 for invalid coordinates, 422 when no route exists, and 429 when a key exceeds its quota. Tiles are cacheable and CDN-friendly; a traffic-dependent route uses Cache-Control: private.

Data flow (optional)

Raw map data is compiled into a partitioned graph with precomputed shortcuts and into a tile pyramid. At query time the service snaps the origin and destination to the nearest routable edges, runs a shortest path over the graph using current traffic weights, and assembles geometry and an estimate. Probe data flows through an ingestion pipeline that updates edge speeds.

  3. An ingestion pipeline aggregates probe data into per-edge speeds for the traffic overlay.

5. Deep dives

Trade-offs and bottlenecks

Plain Dijkstra over a continental graph is too slow per request; precomputation such as contraction hierarchies or customizable route planning turns a query into a short settled search, at the cost of a heavy build and a re-customization step when weights change. Static tiles cache trivially on a CDN, but a traffic-dependent route cannot be cached for long. Partitioning the graph by region enables parallel builds but needs boundary handling for cross-region trips.

Scale estimate: query cost and memory

At 20,000 routes/second, a contraction-hierarchy query settles hundreds of nodes rather than the millions a plain search would, so per-query CPU is a few milliseconds and fleet sizing is dominated by graph replicas held in RAM. A continental graph of about 100 million nodes at roughly 64 bytes each is about 6.4 GB plus shortcuts, which fits in memory per replica, so scale routing by read replicas. Tiles are static, and a CDN absorbs 100,000 or more tile requests/second at a high hit rate, so only misses reach the renderer.

Traffic-aware routing and freshness

Model traffic as a per-edge speed overlay refreshed from aggregated probe data every minute, and read current weights at query time rather than rebuilding the graph. Because changing weights would invalidate contraction shortcuts, use customizable route planning so a traffic update re-customizes the metric in seconds without recomputing the topology. When the overlay is stale or unavailable, fall back to free-flow speeds and label the estimate as traffic-free rather than failing the request.

Correctness, partitioning, and failure

Snap each endpoint to the nearest routable edge with a spatial index such as an R-tree or a geohash grid, and reject a point with no nearby road with 422. Encode turn restrictions and one-way edges in the graph so every returned route is legal. Partition the graph into regional cells with a small overlay of boundary nodes, so a cross-region query stitches cell routes without loading the whole planet. Replicate graph and tiles across zones so a zone loss shifts reads to replicas, and keep no per-user trajectory after the response unless the user consents.

Check the design

NFR1 maps to the precomputed graph and CDN tiles; NFR2 to per-minute traffic customization and encoded restrictions; NFR3 to replicated replicas with a free-flow fallback; NFR4 to key quotas and no trajectory retention. Test it by dropping the traffic store: routes still return with labeled free-flow estimates. Mark an edge impassable and confirm later routes avoid it within the customization interval; verify a cross-region route matches the single-graph answer on a test map.
