File storage

1. Requirements

Functional: upload a new file or version; download a selected version; share a file with selected users.

  1. NFR1: assume 10,000 peak metadata requests/second, with p95 below 200 ms, and resumable uploads up to 10 GB.
  2. NFR2: preserve acknowledged finalized versions through one zone failure.
  3. NFR3: publish only complete, verified versions; concurrent updates to the same base version must not silently overwrite each other.
  4. NFR4: authorize all metadata/content access and revoke new byte downloads within 60 seconds of a sharing change.

2. Out of scope

Desktop synchronization, collaborative editing, cross-user deduplication, and malware detection are excluded. Downloaded copies cannot be revoked. Sharing covers all retained versions.

3. Core entities

File(fileId, ownerId, currentVersion, aclVersion) references immutable Version(fileId, versionId, objectKey, checksum, bytes). Upload(uploadId, ownerId, expectedVersion, state) tracks parts. Grant(fileId, userId, role) stores reader/editor access. The current-version pointer references only a durably stored, checksum-verified object.

4. API

POST /uploads {fileId?, expectedVersion, bytes, checksum} returns uploadId and constrained part URLs. Idempotency-Key retries reuse the session; changed input returns 409. Owner-authorized GET /uploads/{id}?cursor returns state and paginated completed parts/checksums for resumption. POST /uploads/{id}/complete {parts} returns the published version, including on retries; missing parts/checksum mismatch returns 422, stale expectedVersion 409. Uploads require file owner/editor permission. GET /files/{id}/versions/{version}/download checks reader access and returns a short-lived capability. PUT /files/{id}/grants/{userId} {role} and DELETE are file-owner-only, idempotent operations returning 204. Inaccessible resources return 404; quota exhaustion returns 429.

5. Basic design

  1. Authorize an upload and reserve its byte quota and immutable object key.
  2. Upload parts directly; verify the assembled object, then publish its version transactionally.
  3. Owners change grants; authorized readers obtain a capability and download the selected immutable version.

6. Trade-offs and bottlenecks

Proxying bytes through application servers simplifies access checks but ties capacity to transfer bandwidth. Direct transfers require narrow capabilities and bounded revocation. Immutable versions simplify retries and rollback but consume storage. Reject stale base versions rather than merging binary files.

7. Scale estimate

Assume one million uploads/day averaging 10 MB: 10 TB/day, roughly 116 MB/second average ingress. A tenfold peak needs 1.16 GB/second. Thirty-day retention consumes 300 TB raw; three copies need 900 TB before additional version retention. Use multipart object storage, lifecycle policies, and byte quotas; metadata counts cannot size transfer infrastructure.

8. Deep dive 1: Resumable, durable byte transfer

Use uploadId and part number as retry identities; overwriting a part is safe until finalization freezes its manifest. Clients query completed parts and resend only missing ones. Constrain signed URLs by object key, operation, size, and expiration. Verify the assembled object's length and checksum server-side; a part ETag is not necessarily a whole-file checksum. Finalization waits for the storage service's cross-zone durability acknowledgement. Partition metadata by fileId and keep bytes outside the database. Backups protect metadata independently; sweep abandoned uploads only after their sessions expire. The cost is an additional completion round trip and temporary staging storage.

9. Deep dive 2: Atomic publication and bounded sharing

In one replicated transaction, recheck edit permission, compare expectedVersion, insert the immutable version, advance the pointer, and record the completion result. Check an existing completion result before treating a retry as a stale update. A failed transaction leaves an unreferenced object for delayed cleanup, never a partial visible file. Download issuance reads current grants; capabilities expire within 60 seconds of that check beginning. The storage gateway validates them on every range request and terminates streams at expiry, so long downloads must renew authorization. Grant-service failures deny renewal. Audit access without exposing content or signed URLs in logs.

10. Check the design

NFR1–2 → dive 1; NFR3–4 → dive 2. Finalize two uploads against one base: exactly one pointer advance succeeds. Revoke a reader mid-download: expired streams stop, renewal fails, and no unpublished version appears.
