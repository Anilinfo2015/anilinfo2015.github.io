HLD delivery framework

Use one sequence throughout the system-design library: requirements → core entities → API or system interface → high-level design → deep dives. Add a data-flow sketch between the interface and design only when a processing pipeline needs it. Establish a working baseline before optimizing it.

This structure is informed by Hello Interview’s system-design delivery framework. The explanations and worked designs here are original. The LLD template adapts the same sequence to objects and methods rather than distributed services.

Requirements · Core entities · Interface · Optional data flow · High-level design · Deep dives

1. Requirements

Functional requirements

Agree on the few user actions the design must support. Prioritize the essential flows instead of trying to reproduce every feature of a familiar product.

Non-functional requirements

  • State relevant latency, scale, consistency, durability, and availability targets. Label them so the deep dives can refer back to them.
  • Explain which operations need which guarantees; a payment write and a search read need not have the same consistency.
  • Treat workload figures as interview assumptions, not measured product statistics. Calculate capacity when it changes a design decision, not as a mandatory opening exercise.

Out of scope

Name the features excluded from this design. Authentication and resource authorization still apply to every API; an identity platform need not be designed here.

2. Core entities

Identify the domain records, identities, relationships, and invariants needed by the main flows. Keep this a compact model, not a complete database schema or a list of infrastructure products. Refine storage details when the design needs them.

3. API or system interface

Show the operations implied by the requirements, with important inputs, responses, and errors. Use HTTP endpoints for a user-facing service, or event and job contracts for an internal pipeline. Specify ownership checks, pagination, and retry semantics where they affect correctness.

Data flow (optional)

For systems such as crawlers or event aggregation, outline the transformations from input to output before choosing components: discover → fetch → parse → store, for example. Omit this section when the API and ordinary read/write flow already make the work clear. This is a logical pipeline, not a second architecture diagram.

4. High-level design

Draw the smallest complete system and walk each required operation through it. Name the owner of authoritative state and show what is read or written, including the acknowledgement boundary. This baseline must satisfy the functional requirements; explain its limits before adding scale-specific machinery.

5. Deep dives

Choose the topics from the non-functional requirements and the baseline’s concrete weaknesses. The number of dives depends on the problem; two is not a requirement. For each, explain the mechanism, an alternative, the cost, and the behavior during failure.

Trade-offs and bottlenecks

Explain what the baseline makes easy and where it fails. Compare a concrete alternative, rather than listing technologies.

Decision-driven estimates

Put an estimate next to the decision it informs. State assumptions, units, arithmetic, and what would change at a different load. Separate average from peak traffic and raw data from indexes and replicas. Skip calculations that change nothing.

Scaling, correctness, and recovery

Explain the partition key or contention boundary, replication and consistency guarantees, overload behavior, retries, and recovery as relevant to the selected problem. Do not claim “exactly once” without defining the boundary.

Check the design

Trace every functional requirement through the baseline and every non-functional requirement to a design choice or a stated limitation. Include failure scenarios and observable outcomes. A target is a goal to test, not a guarantee created by drawing a cache.

Publishing review

Before publishing: check requirement coverage, arithmetic, API semantics, diagram labels, recovery paths, and links. Remove rehearsed dialogue, unsupported claims about real companies, filler introductions, and repeated conclusions.

All worked HLD answers follow these stages. Longer studies expand individual stages and link back to a separate, scoped worked answer; their capacity assumptions need not match. Start with the URL-shortener walkthrough or the pipeline-oriented web crawler.
