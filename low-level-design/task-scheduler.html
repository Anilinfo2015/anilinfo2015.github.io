Task Scheduler

1. Requirements

Schedule one-off named jobs, claim due work, report completion or failure, and cancel jobs not yet running. Multiple workers share a transactional database. Store UTC instants and use database time for eligibility. Payloads are at most 64 KiB; claims return at most 100 jobs. Indexed polling should inspect due rows rather than scan all completed history.

2. Out of scope

Exclude cron expressions, dependency graphs, priorities, arbitrary uploaded code, and forced interruption of running handlers. Handlers come from a fixed registry. The scheduler promises retryable execution, not exactly-once effects. Jobs may fail permanently after their configured attempt limit.

3. Model and invariants

Scheduler owns job transitions in storage. Job owns handler name, immutable payload, due time, state, attempt count, maximum attempts, and lease generation. Lease records worker, token, and expiry. States are READY, RUNNING, SUCCEEDED, FAILED, and CANCELLED.

Only one lease is current for a job. Its validity interval is [claimedAt,expiresAt); stale tokens cannot update state. Attempts increase on claim, never on heartbeat. Terminal jobs cannot be claimed.

4. Public contract

schedule(handler, payload, dueAt, maxAttempts, key) → Job returns UnknownHandler, InvalidInput, PayloadTooLarge, or KeyConflict; maxAttempts must be 1–10. Identical key/payload returns the original job. claim(workerId, limit) → Lease[] rejects invalid limits with InvalidInput. heartbeat(jobId, token), complete(jobId, token), and fail(jobId, token, errorCode) return updated state or NotFound/StaleLease. An identical completion retry for the successful token returns success. cancel(jobId) → Job is idempotent for cancelled jobs, returns NotFound for unknown IDs, Busy for running jobs, and InvalidState for other terminal states.

5. Core flow

Claim selects READY rows with dueAt ≤ databaseNow, ordered by due time then ID, using row locks with skip-locked behavior. Increment attempts, create a new token, set a 30-second expiry, and commit before invoking handlers outside the transaction.

A valid heartbeat renews expiry to databaseNow plus 30 seconds. Completion records success only if token and unexpired lease match. Failure clears the lease and either marks FAILED at the attempt limit or sets READY with dueAt equal to now plus min(300, 2^(attempts−1)) seconds. A recovery sweep applies that same failure transition to expired RUNNING jobs. It locks and rechecks each row so heartbeat, completion, and expiry cannot all win.

6. Trade-offs and extensions

Leases recover crashed workers but allow overlapping physical executions when an old worker continues after expiry. A resource that supports fencing can reject effects from older generations. Recurrence should create separately identified occurrences rather than repeatedly resetting one completed job.

7. Concurrency and failure handling

Row locks protect claim and lease transitions; durable rows survive scheduler restarts. Worker failure after an external effect but before completion causes possible replay. Pass job ID as the effect's idempotency key when supported. Otherwise handlers must reconcile duplicates themselves. No database lease can roll back an already-sent payment or email.

8. Test cases

A job due at 12:00 becomes claimable exactly then. Two workers claim it once. A completion at expiresAt is stale. With maxAttempts=2, two claimed failures produce FAILED. A crash after claim makes the job retryable only after expiry and backoff. Repeated successful completion creates no transition. Oversized payloads and limit 101 fail before database work; verify the due-state index serves claim queries.
