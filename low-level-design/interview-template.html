LLD delivery framework

Use the same delivery sequence as the HLD template: requirements → core entities → API or system interface → high-level design → deep dives. Here, “high-level design” means the component’s object collaboration and working core logic, not a distributed-service architecture.

This is this repository’s LLD adaptation of Hello Interview’s system-design delivery framework, not a claim that the source prescribes LLD details. An LLD answer must explain who owns state, what operations guarantee, and how the behavior can be tested.

Requirements · Core entities · Interface · Optional data flow · High-level design · Deep dives

1. Requirements

Functional requirements

List the supported operations, business rules, and legal state transitions. Agree on the main use case before introducing classes or patterns.

Non-functional requirements

State the execution model: single-threaded, concurrent in one process, or backed by shared storage. Add relevant constraints such as bounded memory, operation complexity, persistence, and deterministic behavior. Do not import distributed-system scale targets into an in-process problem.

Out of scope

Exclude unrelated UI, networking, persistence, or integrations explicitly. Keep anything required to preserve the stated rules.

2. Core entities

Give each object one responsibility. Identify the owner of mutable state and the conditions that must hold after every operation. Use a small Mermaid class or state diagram.

3. API or system interface

List method signatures, results, and errors. Define duplicate calls, invalid identifiers, and legal state transitions. Prefer interfaces only where behavior actually varies.

Data flow (optional)

For a multi-stage component such as a logging pipeline, show how an input becomes an output before assigning responsibilities to objects. Skip this section when the public methods and collaboration flow are enough.

4. High-level design

Walk the required operations through collaborating objects in implementation order. Include validation, state changes, and the commit or lock boundary. Use pseudocode where prose leaves an algorithm ambiguous, or implement the core methods if the interview requires working code. A class diagram alone is not a working design.

5. Deep dives

Refine the baseline using the requirements: correctness, complexity, concurrency, and relevant extension points. Choose substantive topics rather than a fixed number of patterns. Keep concrete tests here so the design’s guarantees remain checkable.

Trade-offs and extensions

Explain one meaningful design choice and one bounded extension. Do not add a pattern merely to name it.

Concurrency and failure handling

Name the shared resource and protect the whole invariant, not just individual collection operations. Keep external calls outside locks. State what survives process failure.

Test cases

Use concrete input and expected outcomes: the normal flow, an invalid operation, a boundary condition, and a race or retry where relevant. Check the non-functional constraint too.

Publishing review

Before publishing: trace each operation to an owner, check state transitions and money/time units, verify the Mermaid diagram, and remove interview scripts and generic advice. Keep the explanation short enough to review in one sitting.

All worked LLD answers use these stages, including parking lot and LRU cache. The technique playbook explains how to deliver the same sequence under interview constraints.
