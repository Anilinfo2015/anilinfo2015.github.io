Library Management

LLD stages: Requirements → Core entities → API or system interface → High-level design → Deep dives.

1. Requirements

Functional requirements

Catalog titles and physical copies, lend an available copy to a member, return it, and list current loans. A member may have at most five active loans. Loans last fourteen elapsed days, measured using UTC instants rather than local calendar dates.

Non-functional and execution constraints

Concurrent desk terminals use one service backed by transactional storage. Listing uses pages of at most 100 records. Loan records, copy ownership, and member counts must remain consistent across concurrent requests and crashes.

Out of scope

Exclude reservations, renewals, inter-library transfer, fines, payments, and notification delivery. An overdue copy remains checked out until returned. Lost-copy processing is a separate extension; the baseline never makes a copy available merely because its due time passed.

2. Core entities

LibraryService owns lending transitions. Title holds bibliographic metadata; Copy identifies one barcode and its title. Loan owns member, copy, checkout time, due time, and optional return time. A member record owns its active-loan count.

A copy has at most one active loan. The member count equals its unreturned loans and stays between zero and five. Returned loan records are immutable history. The on-time interval is [checkoutAt,dueAt); a still-active loan is overdue at dueAt.

3. API or system interface

checkout(memberId, copyId, requestKey) → Loan returns NotFound, MemberInactive, LoanLimit, CopyUnavailable, or KeyConflict. An identical member/key and payload returns the original loan, including after return. returnCopy(loanId) → Loan returns the existing returned record on duplicate calls or NotFound. Returning by loan ID prevents an old retry from closing a later borrower's loan. listLoans(memberId, cursor, limit) → Page validates the member and page size; cursors order by checkout time and ID.

4. High-level design

LibraryService.checkout begins a transaction and checks the idempotency record. Lock the Member, then the Copy. Recheck membership, count, and active-copy ownership. Read database time, insert a Loan with dueAt fourteen days later, set the copy's active-loan pointer, increment the member count, and persist the request result together. A unique active-loan constraint on copy ID catches any writer bypassing the service.

For return, read the loan's immutable member and copy IDs, lock member then copy then loan, and recheck return status. If already returned, return the stored result. Otherwise set returnedAt, clear the matching copy pointer, and decrement the count in the same transaction. Never decrement based solely on a client-supplied barcode.

5. Deep dives

Trade-offs and extensions

A stored count makes loan-limit checks constant time but requires every lending mutation to maintain it. A reservation extension can add a per-title waiting list; allocating a returned copy must then occur inside the return transaction or a separate atomic claim.

Concurrency and failure handling

Member-first locking protects the limit even when two terminals request different copies. Copy locking protects duplicate lending. A unique member/key record resolves concurrent retries. Transactions and request results survive process failure; a committed checkout with a lost response is safely retrievable using the same key. No external calls occur while locks are held.

Test cases

With four active loans, two concurrent checkouts allow only one additional loan. Two members requesting the same copy produce one success. Returning twice decrements the count once. Replaying an old return after a new checkout leaves the new loan active. A checkout at 2026-09-01T12:00Z is due at 2026-09-15T12:00Z and overdue exactly then. Reject a page size of 101 before querying.
