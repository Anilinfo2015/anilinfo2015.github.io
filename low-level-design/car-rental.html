Car Rental

1. Requirements

Reserve a specific vehicle, cancel before pickup, start a rental, and return the vehicle to its original branch. Concurrent callers share transactional storage. Reservations use UTC half-open intervals [start,end), with positive duration and a maximum of 30 elapsed days. Rental prices use integer minor units and a snapshotted hourly rate. Search returns at most 100 candidates.

2. Out of scope

Exclude one-way rentals, deposits, payments, insurance, damage assessment, and vehicle substitution. Billing records an amount owed, charging commenced hours without a grace period. Reservations cannot guarantee timely return by previous renters.

3. Model and invariants

RentalService owns transitions. Vehicle owns branch, class, serviceability, latest odometer, and active-rental pointer. Reservation owns customer, vehicle, planned interval, hourly rate, version, and state. Rental records actual pickup and return facts.

Non-cancelled planned intervals never overlap for one vehicle. At most one rental physically holds that vehicle. States are RESERVED → ACTIVE → RETURNED or RESERVED → CANCELLED. Odometer readings never decrease.

4. Public contract

search(branchId, vehicleClass, start, end) → Vehicle[] returns up to 100 serviceable vehicles at that branch of that class without overlapping non-cancelled reservations, ordered by ID. Availability is advisory; reserve rechecks. Unknown branch/class returns NotFound; invalid intervals return InvalidInterval.

reserve(customerId, vehicleId, start, end, key) → Reservation returns NotFound, InvalidInterval, Unavailable, or KeyConflict; same key and payload return the stored reservation. pickup(id, customerId, expectedVersion) → Rental returns Forbidden, StaleVersion, PickupWindowClosed, VehicleNotReady, InvalidState, or NotFound. returnVehicle(id, odometer, key) → Invoice requires branch staff authorization and returns InvalidOdometer, InvalidState, NotFound, or KeyConflict. Identical return retries preserve the original timestamp and invoice. cancel(id, customerId, expectedVersion) returns the cancelled reservation or the corresponding identity, version, or state error.

5. Core flow

Reservation locks the vehicle, verifies serviceability, and rechecks planned overlaps using the strict half-open predicate. Persist rate, reservation, and request key together. Cancellation takes the same lock and succeeds only before planned start.

Pickup locks vehicle then reservation and requires database time in [start,end), a serviceable vehicle, and no active-rental pointer. Store the actual pickup time and starting odometer, attach the rental, and increment version atomically.

Return takes the same locks and validates the new odometer against pickup. Read database time once. Bill max(1, ceil(elapsedSeconds / 3600)) × hourlyRate using checked arithmetic, including late hours at the same rate. Persist the invoice, return facts, key, and returned state while clearing the vehicle pointer and updating its odometer.

6. Trade-offs and extensions

Concrete-vehicle booking avoids fleet-capacity allocation logic but makes breakdowns visible. A substitution extension must lock both vehicles in identifier order and verify the replacement interval before changing ownership.

7. Concurrency and failure handling

All writers use vehicle-first locking. An active-rental pointer prevents another pickup; late return cannot clear another rental's pointer. The next reservation may fail pickup with VehicleNotReady, without cancellation. Durable return keys prevent retry-dependent billing. Crashes roll back incomplete transitions.

8. Test cases

[10:00,12:00) and [12:00,14:00) can be reserved together. Pickup exactly at planned end fails. Returning after 3601 seconds at 700 minor units/hour costs 1400. A lower odometer is rejected without releasing the car. Two pickups for one reservation yield one active rental. Duplicate returns yield one invoice. A late previous renter blocks the next pickup; a 31-day reservation is rejected immediately.
